# ADR-012: Сессии с отзывом и refresh-токен

**Статус:** предложено · **Дата:** 2026-08-18

## Контекст

В MVP аутентификация — JWT HS256 сроком на час, без refresh ([PRD](../PRD.md) A-6, [security-and-access.md](../security-and-access.md) §1). Отсюда три проблемы, которые закрывает фаза P1.1 ([PLAN.md](../../PLAN.md)):

- **Отзыва нет.** Выданный токен живёт до истечения: увольнение, компрометация ноутбука или смена роли не обрывают доступ. Частично спасает то, что `current_user` на каждом запросе читает `users` из БД и уважает `is_active`, — но это отзыв пользователя целиком, а не конкретной сессии.
- **Перезагрузка страницы = перелогин.** Токен хранится только в памяти (`frontend/src/hooks/useAuth.tsx`), потому что правило фронтенда запрещает класть JWT в `localStorage`. Без refresh-токена другого места нет.
- **Час — плохой компромисс.** Долгий для украденного токена, короткий для рабочего дня.

Ограничения решения:

- Ломающие изменения `/api/v1` запрещены, только аддитивные ([api-contract.md](../api-contract.md) §8) — существующий `POST /auth/login` обязан продолжать работать как есть.
- Каждый новый эндпоинт получает `require_role`, строку в RBAC-матрице и тест ([.claude/rules/api.md](../../.claude/rules/api.md)).
- `tenant_id` — параметр всех репозиториев (инвариант 7 [CLAUDE.md](../../.claude/CLAUDE.md)).
- JWT не хранится в `localStorage` (правило фронтенда).
- Стенд CPU-bound, память в дефиците — новых тяжёлых сервисов не добавляем.

**OIDC/SSO из объёма P1.1 вынесен.** Решение по провайдеру откладывается до отдельного ADR; настоящая ADR обязана не закрыть ему дорогу — см. «Точка врезки OIDC».

| Список активных сессий в UI | ✅ Готовые данные (устройство, IP, последняя активность) | ❌ Хранит только факт отзыва | ❌ |

## Варианты: где живёт refresh-токен

| Критерий | httpOnly cookie | localStorage | Только память |
|----------|-----------------|--------------|---------------|
| Доступен при XSS | ✅ Нет | ❌ Да | ⚠️ Да, но окно жизни короче |
| Переживает перезагрузку | ✅ | ✅ | ❌ Перелогин остаётся |
| Нужна CSRF-защита | ❌ Да (cookie шлётся браузером сама) | ✅ Не нужна | ✅ Не нужна |
| Соответствует правилу фронтенда | ✅ | ❌ Прямо запрещено | ✅ |
| Когда применять | Нужен долгий вход и защита от XSS | Правило допускает, XSS не в модели угроз | Короткая сессия, простота важнее удобства |

## Решение

**Сессии в PostgreSQL + refresh-токен в httpOnly cookie.**

**Таблица `sessions`** ([data-model.md](../data-model.md) §2): `id`, `tenant_id`, `user_id`, `refresh_hash`, `created_at`, `last_used_at`, `expires_at`, `revoked_at`, `revoked_reason`, `user_agent`, `ip`. В БД лежит sha256 от случайных 32 байт — не сам токен: дамп базы не даёт войти.

**Access-токен** несёт `jti`, равный id сессии. `current_user` одним запросом забирает пользователя вместе с сессией и отвергает токен, если сессия отозвана или истекла. Лишнего обращения к БД не появляется — SELECT по `users` там уже был.

**Сроки:** access 15 минут, refresh 30 дней скользящим окном (`last_used_at` продлевает). Оба — в настройках с префиксом `LYRA_`.

**Ротация refresh — одноразовая.** Каждый `POST /auth/refresh` выдаёт новый refresh и перезаписывает `refresh_hash`. Предъявление уже использованного токена означает, что он украден: сессия отзывается целиком с `revoked_reason=reuse_detected`. Без ротации кража refresh даёт злоумышленнику 30 дней незаметного доступа.

**Cookie:** `httpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/v1/auth` — браузер не шлёт refresh на остальные эндпоинты. CSRF — double-submit: несекретная cookie `csrf_token` плюс заголовок `X-CSRF-Token`, обязательный для `POST /auth/refresh` и `POST /auth/logout`. `SameSite=Lax` отсекает основную массу межсайтовых POST, double-submit — второй рубеж на случай поддоменов.

**Новые эндпоинты** (аддитивно, api-contract §1): `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/sessions`, `DELETE /auth/sessions/{id}`. Последние два — viewer, и только над своими сессиями (как `/chat/sessions`: чужая → 403).

**Вход по паролю остаётся основным способом.** `POST /auth/login` дополнительно заводит сессию и ставит cookie; форма ответа не меняется.

**Точка врезки OIDC.** Сессия создаётся функцией `issue_session(user, *, user_agent, ip)`, ничего не знающей о способе аутентификации. Будущий OIDC-callback вызывает её же — таблица, ротация, отзыв и cookie переиспользуются без изменений.

**Чистка.** Истёкшие и давно отозванные сессии удаляет периодическая задача рядом с `gc_superseded` ([ADR-008](ADR-008-task-queue-celery-vs-rq.md)).

## Последствия

- (+) Отзыв мгновенный и без второй точки отказа: Redis остаётся необязательным для входа.
- (+) Перезагрузка страницы больше не разлогинивает — исчезает главная претензия к демо.
- (+) Появляются «мои устройства» и «выйти везде», а заодно готовые данные для аудита P1.4.
- (+) Ротация с детектом повторного использования превращает кражу refresh-токена из тихого долгого доступа в обрыв сессии.
- (+) Access живёт 15 минут вместо часа — окно для украденного токена вчетверо у́же.
- (−) Cookie тянет за собой CSRF-защиту, `credentials` в CORS и правку прокси Vite. Это цена `httpOnly`; альтернатива — `localStorage` — запрещена правилом фронтенда.
- (−) Новая таблица растёт вместе с числом входов; смягчение — периодическая чистка и индекс по `expires_at`.
- (−) Отзыв стоит join на каждом аутентифицированном запросе. Смягчение: join к запросу, который уже выполняется, и индекс по первичному ключу сессии.
- (−) Access в 15 минут учащает обновление; фронту нужен единый перехват 401 ровно с одной попыткой refresh, иначе при протухшей сессии получится шторм запросов. Это требование к реализации, а не побочный эффект.
- (−) Логика ветвится: пароль сейчас, OIDC потом. Смягчение — `issue_session` как единственная точка выдачи сессии.
